# Model Limitations Register

Updated 2026-11-23 from source inspection of `simulator/cp-closed-loop.cc`, `cpstudy/closed_loop.py`, `cpstudy/receiver.py`, configuration files, and the preserved trace audit. Each item is a claim boundary for the manuscript rewrite.

| ID | Model or evidence limit | What is actually implemented or observed | Required manuscript treatment |
|---|---|---|---|
| L01 | Cryptographic work | Configurable deterministic verification delay; signatures are assumed valid. No ECDSA, certificate chain, revocation, VPKI, key lookup, or crypto failure simulation. | Call the parameter a synthetic verification service-time budget. Remove “calibrated ECDSA,” HSM/ECU performance, and claims about mandated per-message compute cost. |
| L02 | Processor measurement | Simulated service intervals and queue states are recorded; no real CPU cycles, wall-clock busy fraction, or hardware utilization is measured. | Never report percent CPU cycles wasted or physical processor saturation. Keep offered rho distinct from worker busy fraction. |
| L03 | Queue discipline and expiry | One non-preemptive FCFS verification worker; 32 waiting slots plus the active message. Frames are not pruned before verification; expiry is classified after verification and again after fixed fusion delay. | Describe this as the modeled software rule. Do not generalize it to standard automotive ECU firmware. Queue depth alone does not establish how long every queued message has waited. |
| L04 | Fusion | Fusion availability is a fixed delay with no shared fusion worker or GPU queue. | Do not claim processor-wide or end-to-end compute contention beyond the modeled verification worker. |
| L05 | Inference and signing | Fixed configured delays precede data transmission; no sensor pipeline, signing implementation, or measured execution. | Label as fixed synthetic delay inputs. |
| L06 | Service variability | Main runs use service coefficient of variation 0; verification service is deterministic at each configured budget. | Do not generalize to variable or hardware-specific crypto workloads. List service variability as untested. |
| L07 | Payloads and messages | 1100-byte experiment payload plus 100-byte size overhead; messages are not encoded CPM or IEEE 1609.2 objects. | Call payload and security bytes synthetic size fixtures. No CPM conformance or message-level perception claim. |
| L08 | Mobility | Constant-velocity synthetic flows; configured speed is 10 m/s in both the intersection and highway studies. Nodes recycle at scenario boundaries. No SUMO, traffic lights, car following, or measured trajectories. | Replace “realistic” and 90 km/h highway statements with controlled synthetic geometry and configured speed. |
| L09 | Perception and safety | The model has source opportunities and authenticated-update timing, not object detection, tracking accuracy, hazard coverage, collision avoidance, or safety outcomes. | Refer only to timely source-update availability in the simulation. Remove safety benefit, safety update, and deployment-efficacy claims. |
| L10 | Radio channel | ns-3.46.1 802.11p PHY, AdhocWifiMac, fixed 6 Mbps / 10 MHz, 23 dBm, constant propagation delay, log-distance loss exponent 2.5 and reference loss 47.86 dB. No building blockage, shadowing, calibrated NLOS, or measured channel traces. Source does not set a project-specific receiver-sensitivity threshold. | Report configured settings only. Remove “realistic” channel, standards compliance, and -85 dBm sensitivity assertions unless the exact build default is independently established. |
| L11 | Traffic process | Periodic 10 Hz opportunity demand with seeded phase; controller admission is quantized to opportunity ticks. It is not a Poisson arrival process. | M/G/1 equations are conditional analytical references, not validated predictors for the experiment traces. |
| L12 | Offered utilization | Phase 3 counts fixed-policy data receptions in `[1 s, 5 s)` and multiplies receiver arrival rate by configured mean service time. Two 3 ms seed traces were unavailable/truncated and matched 1 ms fixed-policy traces were reused. | Name this offered rho; disclose trace reuse and do not equate it to measured CPU utilization or queue stability. |
| L13 | Radio comparator | `radio` is a project-specific CBR AIMD controller. `dcc` implements a bounded adaptive core and single-service airtime mapping, without full ITS-G5 facilities behavior or conformance certification. | Keep the policy names distinct. Describe `dcc` as the project DCC mapping / DCC-inspired comparator, not an ETSI-compliant implementation. |
| L14 | Backlog attribution | In the trigger file, 1,242 of 1,330 joint decreases were classified `backlog_only` (93.38%). This is a control-decision attribution, not evidence that an isolated neighbor burst caused the outcome. | Retain the count as descriptive trigger attribution only. Remove “isolated outlier” causal mechanism unless a new auditable calculation supports it. |
| L15 | Calibrated aggregation | The calibrated code takes the cross-sectional arithmetic mean of currently fresh neighbor reports at each control update; it does not compute a temporal moving average. | Replace manuscript references to temporal moving-average smoothing with the implemented aggregation rule. |
| L16 | Stress cell completeness | Ten of 75 stress run traces are incomplete; verified cell sizes range from 1 to 3. | Report cell-specific audited n and uncertainty. Do not portray the stress table as 75 fully verified outcomes or use n=1/2 cells for broad mechanism claims. |
| L17 | Provenance | Historical major-revision summaries lack embedded source revision, full configuration snapshot/hash, and simulator binary hash. | Disclose this gap. Do not infer run-time hashes from the current workspace source. |
| L18 | DCC capacity arithmetic | The manuscript's 25-node calculation counts the receiver among potential senders although the radio model excludes self reception. Dynamic neighborhoods, loss, heterogeneous arrival rates, and queue state also violate the fixed equal-share premise. | Remove “Theorem 2.” At most give a clearly labeled conditional service-load illustration; do not call it a general TOSR bound or explain the observed results with it. |
| L19 | Processor-cycle waste | No analysis estimates how much verification service time ended on expired work over the run. Terminal states only identify outcomes. | Remove the “100% wasted cycles” empirical statement. Any future percentage requires an explicit numerator/denominator from verification intervals and a declared meaning of “wasted.” |
| L20 | Sensitivity coverage | There is a verification-time sweep and a threshold ablation, but no comprehensive sweep over worker count, queue capacity, service variability, range, blockage, payload, feedback loss/staleness/overhead, or deadline. | Keep conclusions bounded to tested values; list omitted sensitivities as future work, not as established behavior. |
